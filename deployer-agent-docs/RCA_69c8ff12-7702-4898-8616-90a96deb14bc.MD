# RCA — Cloudflare 520 ("origin sent a response Cloudflare could not parse") + general slowness
**App:** worksite-command (INDIAN TRADE LINKS ERP) · FastAPI + React + MongoDB
**Deployment:** c416f495-cf4b-4fb4-a302-c9d692b70f82 · **Active run:** 69c8ff12-7702-4898-8616-90a96deb14bc
**Tier:** tier_0 (Starter) — cpu 250m limit, **memory 512Mi limit**, 2 replicas, HPA disabled
**Frontend:** Cloudflare (static from R2; worker proxies /api to the k8s backend)

## Summary
The 520s are NOT a frontend/route bug. The production backend is failing to return a valid HTTP response for two proven, compounding reasons, both of which produce exactly the "empty / unparseable origin response" Cloudflare reports:

1. **Both backend replicas are being OOMKilled (exit 137) at the 512Mi tier limit** — a worker killed mid-request drops the connection with no valid response → Cloudflare 520.
2. **The backend runs a SINGLE uvicorn worker (one event loop) and performs CPU-heavy, synchronous work ON that event loop** (WeasyPrint PDF, openpyxl XLSX, plus an in-process scheduler). While that blocks, every other request — including the nginx `/health` probe — times out at the origin → nginx returns an empty/bad-gateway response → Cloudflare 520, and unrelated /api calls on the same screen stall or drop. This also explains the general slowness (all requests are serialized through one loop) and why some calls on a page succeed while others fail at the same instant.

## Evidence (production)

### 1. OOMKills — proven
`get_pod_events` (run 69c8ff12), kill_findings:
```
pod ...-jttxf  last terminated: OOMKilled (exit 137) at 2026-10-26T18:30:11Z, restarts=1
pod ...-ntl6g  last terminated: OOMKilled (exit 137) at 2026-10-26T18:30:15Z, restarts=1
```
Both replicas (the entire fleet) OOMKilled within ~4s of each other. `get_tier` confirms the ceiling they hit: memory_limit **512Mi**. Reason is explicitly **OOMKilled**, not a bare exit 137 — i.e. the container exceeded the tier's memory limit. The near-simultaneous kill of both replicas points at correlated memory load (a heavy export and/or the in-process scheduler firing on both pods at once — see #4).

### 2. Event loop blocked → origin timeouts — proven
`fetch_app_logs` (run 69c8ff12) shows repeated nginx→backend upstream timeouts, even on the lightweight health probe:
```
[error] upstream timed out (110: Connection timed out) while reading response header
from upstream, request: "GET /health HTTP/1.1", upstream: "http://127.0.0.1:8001/health"
```
Many of these over ~05:00–05:20Z. If the backend cannot answer `/health` within nginx's read timeout, it was not answering anything — the single event loop was blocked. nginx then returns an empty/gateway error upstream and Cloudflare renders it as a 520.

### 3. Single worker + blocking, non-offloaded CPU work — proven from source
Production backend command (supervisord.conf, baked into the image):
```
command=/root/.venv/bin/uvicorn server:app --host 0.0.0.0 --port 8001 --workers 1 --reload
```
- `--workers 1` → **one process, one event loop**. (`--reload` is stripped at runtime by entrypoint.sh, so reload is NOT active in prod — not an issue.)
- Heavy synchronous calls run directly on the loop, with **no** `run_in_executor` / `asyncio.to_thread` / `BackgroundTask` / `StreamingResponse` anywhere in backend source (grep returned none):
  - `backend/pdf_generator.py:164` → `return HTML(string=html).write_pdf()` (WeasyPrint — CPU & memory heavy)
  - `backend/exports.py:453` → `wb.save(buf)` (openpyxl workbook built fully in memory)
- Runtime logs confirm this work actually runs in prod: `fontTools.subset` lines (WeasyPrint font subsetting) and `docs.google.com/.../export?format=csv` fetches.

WeasyPrint + openpyxl are both memory-hungry and both block the loop. On a 512Mi cap this is the direct driver of #1 (OOM) and #2 (loop stall) simultaneously.

### 4. In-process scheduler runs in every replica — contributing factor
`backend/scheduler.py` uses `AsyncIOScheduler` inside the API process, with ~15 jobs including `_onedrive_push_job` every 2 min and a Google-Sheets attendance sync every 15 min. Because it is in-process, it runs in **both** replicas (work and memory doubled) and competes for the same single event loop — consistent with both pods OOMing together and with periodic stalls.

### 5. MongoDB — NOT the proven cause
`backend/core.py:24` → `client = AsyncIOMotorClient(MONGO_URL)` with **default** pool settings (no maxPoolSize/timeout tuning). No connection-pool-exhaustion or server-selection-timeout errors appear in the logs. I did not find evidence that Mongo pool exhaustion is causing the 520s. The heavy list endpoints do large scans (`page_size=200` with multi-field `search_keys`), which adds latency/memory but is secondary to #1–#3. Treat DB indexing as an optimization, not the root cause.

### 6. Secondary (unrelated to 520) — email sending broken
Many `erp.email - ERROR - ... You can only send testing emails to your own address ... verify a domain at resend.com/domains`. Resend is in sandbox/test mode. Not a cause of the 520s, but a real, separate production bug.

## Live state right now
`preview_health_check` on `/api/` → 200 in 572ms (`{"service":"Corporate ERP API"}`). The app is currently up; the failures are intermittent, triggered by memory spikes / loop-blocking episodes (heavy exports, scheduler bursts), exactly matching "recurs across modules."

## Root cause (one line)
Heavy synchronous WeasyPrint/openpyxl work (and an in-process scheduler) running on a **single uvicorn event loop** inside a **512Mi** pod → the worker either OOMKills mid-response or blocks the loop past the origin read-timeout → nginx emits an empty/invalid response → Cloudflare 520; the single-loop serialization also causes the general slowness.

## Fixes

### A. Code (E1 implements) — the real fix
1. **Offload all blocking CPU work off the event loop.** Wrap `HTML(...).write_pdf()` (pdf_generator.py) and the openpyxl build+`wb.save()` (exports.py) in `await asyncio.to_thread(...)` (or a bounded `ThreadPoolExecutor`). This alone stops one export from stalling every other request and the `/health` probe.
2. **Cut export memory.** Use openpyxl `Workbook(write_only=True)` and stream rows; return via `StreamingResponse`; free WeasyPrint/document objects promptly; for very large PDFs prefer the existing ReportLab fallback. Bound concurrency (e.g. a semaphore) so two simultaneous exports can't both blow the memory cap.
3. **Move the scheduler out of the API process / stop it running in every replica.** Run APScheduler in a single dedicated worker or guard it to one replica; ensure its jobs also offload blocking work. Reconsider the 2-minute `_onedrive_push_job` cadence.
4. **Add MongoDB indexes** for the hot list/report endpoints (the `page_size=200` + multi-field search queries) and set explicit Motor pool limits/timeouts. Optimization, not root cause.
5. (Separate bug) Fix email: verify a domain in Resend and set the `from` address to that domain, or the user updates the Resend key — see B/C.

### B. User — Resources (tier)
Raise the tier from **tier_0 (512Mi)** to at least **tier_1** in Deployment Panel → Resources. OOMKilled at the 512Mi limit is proven; WeasyPrint+openpyxl+scheduler need more headroom. Do this together with A — raising memory without offloading the blocking work will reduce OOMs but not the loop-stall 520s/slowness. (Note: simply adding uvicorn workers would multiply memory and worsen OOM at this tier — offloading + more memory is the correct combination.)

### C. User — third-party (Resend), for the email errors only
Verify a sending domain at resend.com/domains and update the `from`/API key accordingly in Secrets. Unrelated to the 520s.
